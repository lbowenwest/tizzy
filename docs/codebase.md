# Tizzy: codebase architecture

This document records the agreed technical design. Player-facing rules and open game decisions live in [design.md](design.md).

## Stack and deployment

Use React and TypeScript with Vite, plain CSS, Vitest for logic tests, and Playwright for browser tests. Deploy the built site and its word data as static assets. The app needs no backend, database, live dictionary API, UI kit, or general-purpose state-management library. Charts use uPlot (MIT, about 22 kB gzipped), chosen by the owner on 2026-10-15 as a lightweight graphing library; it is imported dynamically so it loads only when a chart is shown. Browser localStorage remembers settings and finished-word history; it also stores daily progress and transcripts, but does not provide cross-device sync. Unfinished practice rounds are not persisted.

A static client is enough for unlimited solo practice. It also means answers are available in client-side assets/state: this is not a tamper-proof competitive game. Authoritative scoring or anti-cheat would require a different trust boundary, not merely another browser module.

## Modules and ownership

| Module | Canonical responsibility | Interface to its caller |
| --- | --- | --- |
| Word-list preparation | Extract, filter, and package ESDB data and attribution before deployment; choose qualifying clue words using the puzzle evaluator | Versioned accepted-guess, curated-answer and clue assets for supported lengths |
| Puzzle evaluator | Candidate validity, duplicate-aware letter feedback and clue contradictions | Answer + submitted guess + accepted words → validity or feedback; clue + word → first contradiction or none; independent of React and clocks |
| Round controller | Current puzzle, attempts, success/failure transitions, rule snapshot, format progression, clock policies, expiry precedence | State + player/clock action → next state and observable outcome |
| Clock integration | Observe word and optional overall-round deadlines; deliver expiry actions | Expiry events, without deciding game outcomes |
| Attempt history | Finished-word records, retention, per-group statistics and clearing | Finished round → upserted record; stored records → per-group summary |
| Guess analysis | Replay prior evidence, partition candidate answers by feedback, compare legal guesses | `analysis.ts`: finished round + word data → information breakdown or clue explanation; active rounds return null |
| React presentation | Board, input, settings, presets, results, and responsive keyboard/touch interaction | Renders round state and dispatches actions; never duplicates game rules |

React's built-in state facilities are sufficient to host the controller; no second state-management system is needed. Presets are the practice configurations players can choose, and they are ordinary `Rules` values rather than separate game implementations. The controller stays general (every clock scope, guess limit and unknown-word policy), so a new preset is a data change. Take a rules snapshot on round start and persist the chosen preset key separately in localStorage. A single-word session or a 4→5→6 sequence uses the same puzzle evaluator and word controller; the sequence is progression policy, not a new guessing algorithm.

The controller owns whether an invalid candidate is rejected, consumes an unscored attempt, or ends the word, whether a word timeout requires a same-length replacement, and whether an overall timeout ends the multi-word round. Clock integration schedules observations from deadlines rather than treating browser interval ticks as authoritative elapsed time. If both deadlines have expired, the controller gives overall-round expiry precedence. The approved background policy is elapsed wall time during active play: timers continue during suspension, tab switches and dialogs; a paused result stays paused. Reconcile on visibility/focus/pageshow and before player transitions, using the latest state rather than a captured word. Ordinary failure results still expire an unfinished sequence. Solves and give-ups pause the overall clock; `isRoundClockPaused` is the shared controller, observer and presentation predicate. The result's existing end timestamp anchors its precise remaining budget, and continuation rebases its deadline on current wall time without a refill. Successful final completion stops it.

Clue puzzles reuse the same evaluator at build time and in play. `scripts/build-wordlists.ts` imports `evaluateGuess` from `src/game.ts` to choose clues, so the strict uniqueness check and the player's feedback can never disagree; clue assets store only words. `wordLists.ts` loads them with the other lists, as `WordData.clues`. A `clue` rule (meaningful only for single words; `normalizeRules` resets it for sequences) makes `newWord` pick an answer and one of its clues, and the round carries the clue as a `ScoredGuess` (a word with its feedback). `newWord` uses a clue only after confirming that no other word in `data.guesses[length]` (the same list `submitGuess` validates against) fits it, about one pass of that list; it skips any stored clue that fails. The uniqueness invariant therefore holds even with stale, mismatched or test-routed data, and a known non-answer word always has a contradiction. The controller skips the first-letter check for such a round. A known word other than the answer becomes a rejected `Guess` that spends an attempt with no feedback and carries its contradiction reason, which the evaluator derives by comparing the word with the clue. Keyboard knowledge comes from the clue plus scored guesses; history counts rejected tries as guesses but not as unknown words. Presentation only renders the clue row, rejected rows and reasons.

History observes controller results; it is not a second rules path. `game.ts` stamps each word's `startedAt` and its round's `roundStartedAt`, and depends on neither history nor presets. `src/history.ts` derives a record from a finished round, including its group from `getPresetKey` on the round's snapshotted rules (a round matching no preset is not recorded, and stored records whose group is not a current preset are dropped), and upserts it by word identity so repeated observations and a later round expiry replace rather than duplicate. It keeps the newest 1,000 records and computes statistics from records alone. Like `preferences.ts`, it pairs pure parse/update/summary functions with thin localStorage wrappers that fall back safely; each save re-reads storage so another open tab's records are not overwritten wholesale. Play is the only recorder: it records whenever the round it holds is not playing.

### Current source ownership

- `src/analysis.ts`: pure finished-word analysis using the existing duplicate-aware evaluator. Expected values depend on candidate answers only; actual feedback filters the next candidate set. `src/AnalysisDialog.tsx` renders the report and its metric explanations. `Play` holds a finished-round snapshot only while the dialog is open; analysis runs on demand, without adding work during typing or altering clock rules. Practice transcripts are not persisted; daily transcripts are retained with the completed course. `analysis.worker.ts` runs the same pure analysis off the main thread and is terminated when the dialog closes. No-hint six-letter analysis measured about 8.2 seconds with the full 4,761-answer / 8,492-guess lists, so synchronous dialog computation would block interaction.
- `src/game.ts`: pure evaluation, transitions, deep rule snapshots and `advanceClock` deadline reconciliation. Word/round deadlines and end timestamps are state, not interval counters. `giveUp` reconciles deadlines before ending an active unlimited word; existing failure/continuation rules preserve sequence length and resume the paused overall budget with a rebased deadline. A null `maxGuesses` means Unlimited and suppresses attempt exhaustion without changing deadline precedence or scoring.
- `src/useRoundClock.ts`: cleaned-up browser observations and wake-up events. It schedules a display refresh and calls the controller with wall time; no second expiry policy.
- `scripts/build-wordlists.ts`: pinned-source checks, list curation and clue selection (see [wordlist.md](wordlist.md#clue-puzzles)); clue feedback comes from `evaluateGuess`, never a second evaluator.
- `src/presets.ts`: the preset list (keys are history groups and must stay stable; each preset names its mode and variant, from which its label is built), key-to-rules lookup, play-equivalent rule equality for preset recognition/pending notices (via `normalizeRules` in `game.ts`, which ignores sequence length, off-clock seconds and single-word round time), and human-readable rule previews.
- `src/preferences.ts`: validated local persistence of the theme and preset key; rules saved before presets-only map to the preset they match, otherwise the default.
- `src/history.ts`: finished-word records, upsert by word identity, newest-1,000 retention, per-group statistics (including the guess distribution sized from the preset's limit) and safe localStorage wrappers. `src/StatsDialog.tsx` only reads, presents and clears them (with `src/SolveTimes.tsx` building one-try presets' trend and bell curve as uPlot charts in the page theme's colours), tabbing by each preset's `mode` and `variant` from `src/presets.ts`.
- `src/Play.tsx` and `src/Settings.tsx`: rendering, non-editable guess display, touch-key dispatch, guarded physical-keyboard/paste events and the preset preview. Keyboard feedback uses the controller's strongest per-letter evidence; no text field is needed during play. The per-word guess limit drives controller exhaustion and finite board rows. Unlimited rows grow from actual history inside a bounded, focusable scrolling viewport; all checked and unfinished rows remain available after expiry. Only presentation owns scrolling; settings actions stay outside the scrolling form fields.

### Daily ownership

- `game.ts` owns `firstLetter`, candidate validation and `startWord`; random practice and scheduled daily words use the same round shape and submission path. Clue mode normalizes the first-letter rule off. Existing preset keys keep their old hint behaviour; four new no-hint keys keep their stats separate.
- `Play.tsx` exports the shared controlled `Puzzle` board/input. `Play` owns practice rounds, deadline observation and word-history recording. `DailyClimb.tsx` owns daily progression and presentation, using the same board without Give up or mid-course analysis. Its count-up display derives from timestamps; interval callbacks do not accumulate time.
- `daily.ts` owns UTC dates, versioned course selection, start/continue, elapsed totals, spoiler-free text, saved-run parsing and daily statistics. The `tizzy-daily-v1` localStorage store retains 1,000 runs with three staged `Round` snapshots. Parsing rebuilds feedback and rules through `submitGuess` using scheduled answers; malformed records are discarded. Saving re-reads the archive and only extends a matching existing guess prefix, preventing ordinary stale-tab rewind or replacement. Storage events update other open tabs. Browser storage is not a server-side lock or anti-cheat mechanism.
- `src/daily-v1.json` freezes the existing curated answer pools sorted by SHA-256 of `tizzy-daily-v1|` plus each word. Epoch is 2026-10-16 UTC. At each length, day index `d` selects `(2*d + variantOffset) mod poolLength`, with offset 0 for given and 1 for hidden. **Never regenerate or reorder this file with dictionary updates.** A future schedule needs a new version and an explicit date boundary; tests check the pinned words remain in both accepted and curated lists.
- Daily's selected date pins once a run exists, so midnight cannot silently replace a restored active word. Only solved-to-next transitions create new timestamps. Completed daily results do not go through practice history. Daily Stats can reopen transcripts and run analysis on demand.

## Word-list preparation

Use the [English Speller Database (ESDB, formerly SCOWL)](https://github.com/en-wl/wordlist). Extract and filter its words before deployment, producing a broad accepted-guess set and a curated answer set for 4, 5, and 6 letters. The game does not query an external dictionary at runtime. Pin the ESDB source revision used for the assets to make regeneration reproducible. Include the applicable [copyright and permission notice](https://github.com/en-wl/wordlist/blob/v2/Copyright) with redistributed lists.

## Verification boundaries

- **Vitest through the puzzle evaluator:** candidate validity, first-letter and length constraints, exact/misplaced/absent letters, and duplicate letters.
- **Vitest through the puzzle evaluator (clues):** a word gets a contradiction reason exactly when its feedback against the clue differs from the clue's own, across duplicates and every tile state.
- **Vitest over generated data:** every stored clue is a different curated answer, shows at most half right-place letters and is fitted by no other accepted guess.
- **Vitest through the round controller:** accepted guesses, all three invalid-word policies, configurable attempt exhaustion, unlimited guesses at every final length, final-guess wins, legacy guess-limit defaults, per-guess resets versus per-word continuity, word versus overall expiry, simultaneous expiry, same-length replacement, length advancement, settings snapshots, and clue rounds (no first letter, rejected tries, attempts loss).
- **Vitest through the history module:** record derivation from real controller transitions, idempotent upserts, expiry replacement, retention, grouping, statistics and malformed storage.
- **Playwright in the browser:** keyboard and touch-friendly input, desktop/mobile layouts, settings and presets, untimed single-word play, and timed multi-word play.

Keep the game rules testable through the same controller interface React uses. Presentation tests should cover interaction and layout rather than reimplementing the puzzle evaluator's exhaustive cases.
